## なぜこれが重要なのか

あなたのデータは、他人のコンピュータではなく、あなたの家に住むべきである。クラウドサービスは確かに便利だが、月額料金、プライバシー上の取引、そして企業がいつでも条件を変え、値上げし、停止しうるという危険が付いてくる。Town OS は、支配権を手放さずに同じ便利さを与える。

使うのに技術者である必要はない。USB ドライブを挿して電源を入れれば、動くシステムがそこにある。アップグレードは USB ドライブの差し替え。リセットは再起動。何かがおかしくなっても、いつでも動く状態に戻れる —— 自分を締め出してしまうことはない。

Town OS は、誰もが家族のために家でサービスを動かす手助けができるように作られている。親のためにメディアサーバーを立てる、子どもの端末をスパイウェアから守る、自分のウェブサイトをホストする —— どれもクラウド事業者に許可を求めることなくできる。

## 既存の機能と予定している機能

パッケージングはストレージおよびネットワークと完全に統合されており、必要に応じてリソースを作る。UPnP によるポートの開放、パッケージごとのネットワークコントローラを介したポートフォワードの管理、トンネルの確立などが含まれる。

Town OS は自前のローカルリゾルバ（Rolodex）を動かし、それをシステム自身がプログラムする。インストールされたパッケージはすべてプライベートな TLD の下に名前を得る（`plex.default.home`）ので、サービスにはポート番号ではなく名前で到達できる。同じリゾルバがルーター相当のフィルタリングも行う —— DNSBL のドメインブロックリストと RBL の逆引き IP リストが、あなたの選んだ提供者のゾーンに対して必要に応じて問い合わされ（Spamhaus、SURBL、URIBL などがワンクリックで追加できる形で用意されている）、加えて自分で手入れするローカルのブロックリストもある。これが、子どものタブレットや家じゅうをアドウェアとスパイウェアから守るやり方であり、フィードのダウンロードも、裏で何かをキャッシュすることもない。

ネットワークは WireGuard のオーバーレイとして切り出せる。各ネットワークは自分の TLD と自分のオーバーレイのサブネットを持ち、その分割は本物である。LAN 上のノートパソコンはすべてのネットワークを解決できるが、一つのネットワークにトンネルで入った電話は、そのネットワークと公共のインターネットだけを解決し、それ以外は解決しない —— 兄弟のネットワークの名前は、その電話にとっては単に存在しない。ピアは UI から登録する（あるいは、一つのネットワークでのピア登録以外に何も許可していないアカウントからでもよい）。すぐ取り込める設定が渡され、実際に接続した宛先のアドレスが返されるので、同じ Wi-Fi 上の電話が公開 IP を経由して折り返すよう指示されることはない。登録には TTL があり自分で期限切れになるので、放置された端末がオーバーレイのアドレスを永久に占め続けることはない。Networks の画面には、いま誰が接続しているか —— 端末、アカウント、オーバーレイのアドレス、直近のハンドシェイクと転送量 —— が切断ボタン付きで並ぶ。

HTTP のものはすべて、名前によって HTTPS で提供される。Town OS は自前の認証局を動かす。各パッケージと各 page はその FQDN のリーフ証明書を得て、単一の共有 ingress が `:443` で TLS を終端し、SNI によって正しいサービスを選ぶ。`/tls/ca.crt` からルート証明書を一度取ってくれば、ブラウザは文句を言わなくなる。ingress はすべてのインターフェイスで listen し、アドレスではなく名前でルーティングするので、同じ証明書が LAN からでも WireGuard のトンネルからでも通用する。

ストレージシステムはパッケージングシステムと一緒に設計されており、アップグレードに加えて、一時的なアンインストールと後日の復元にも対応する。ストレージはパッケージごとに独立して区切られているので、コストと可用性に基づいて優先順位を付けた災害対策の戦略を立てられる。クォータは、ストレージの必要量がユーザーの意表を突かないようにするために使う。

あなたのファイルにも自分の家ができる。オブジェクトストレージ（gfeh）はネットワークごとに一つのデーモンを動かし、それぞれが自分のユーザー、自分の権限、自分の取り分のディスクを持ち、同じファイルを一度に四通りに公開する —— S3 エンドポイント、素の HTTPS、Google Drive 互換のビュー、そして IPFS —— すべて名前によって、すべて同じ ingress と同じ証明書の後ろで。ユーザーは平坦な一覧ではなく木であり、誰かに枝とその下のすべてを渡せる。ファイルはリンクとして共有でき、あとで取り消せる。Object Storage の画面には、各ネットワークの区画、その中に誰がいるか、誰が何に到達できるか、そして現在公開されているすべてのリンクが表示される。この機械を立ち上げた人は自動的に home の区画に置かれる。自分自身に権限を与えなければ使えないファイル置き場は、ファイル置き場ではないからである。

パッケージはユーザーに入力を求めることができる —— debconf に似ているが、UI を通じて行う（スクリーンショットを見てほしい）。これらはテンプレート変数であり、コンテナイメージの設定やネットワークの管理に使える。質問には型があり、その型は実際に仕事をする。ポートは空欄にすれば自動で割り当てられ、secret は自分でひねり出せと言われる代わりに 256 ビットのエントロピーで生成され、真偽値はチェックボックスとして描かれ、質問は任意と印を付けられるので空の回答が「設定しないままにする」を意味するようにでき、上級者向けの一群は `show_if` でチェックボックスの後ろに畳んでおけるのでダイアログが入力欄の壁にならない。`oauth` の質問は、かつて手で走らせていたシェルスクリプトを置き換える。Connect を押し、提供元自身のページで承認すれば、トークンが欄に落ちてくる —— しかも Town OS には提供元の一覧が焼き込まれていない。URL はパッケージ自身が名指しするからである。

パッケージは Go の `text/template` によるファイルテンプレートも定義でき、インストール時にボリュームへ展開される。そこではユーザーの回答、パッケージのメタデータ、システムの情報（ホスト名、各 IP）を参照できる。テンプレートはボリュームの初期投入の後、サービスの起動の前に適用され、既存のファイルが上書きされることは決してない。パッケージは他のパッケージに依存できる。依存関係は自動的にインストールされ、親とプライベートなコンテナネットワークを共有するのでホストのポートを介さず名前で通信し、インストール時に互いに値を渡せ（データベースのコンテナ名とポートなど）、双方が同意した場合にストレージのボリュームを共有できる。詳しくは[パッケージリポジトリ](https://github.com/town-os/default-packages)を参照のこと。リポジトリはプライベートなリポジトリ一覧で丸ごと差し替えることもできる —— ゲーム仲間や、あなたが面倒を見る家族などにうってつけである。この方面は大きく広がる見込みである。

サービスにはどれも十分なログと監督が備わっている。この情報にアクセスするための快適な UI があり、技術者でないユーザーが安全に読めるような見せ方をしている。サービスは木として示される —— パッケージと、その下に入れ子になった依存関係 —— ので、木ごとまとめて操作したり、その中のすべてのユニットのログを一つのビューで統合して読んだりできる。管理者と一般ユーザーのアカウントは分かれている。その気になれば、親のために Plex（や似たもの）を動かす手助けができるし、彼らをスパイウェアから守ることもできる。「管理者」と「一般ユーザー」の間には権限付与（grant）があり、チェックを一つ入れれば、あるアカウントに一つのネットワークへの端末登録だけを、あるいはそのネットワークのファイル置き場の運用だけを許せる。権限付与が解錠しないものは既定で閉じたままなので、来年追加される能力が既存のアカウントに黙って渡ることはない。

機械の更新は、その作業ぶりを見せてくれる。システムコントローラは起動を始める前にポートをバインドするので、UI は進捗を生で流す —— コントローラ、DNS、システムサービス、そして各パッケージが再起動されるたびに一行 —— 死んだポートに向かってスピナーを回すのではなく。プロセスの化身ごとに id を付けるので、ブラウザは「古い版がまだ応答している」と「新しい版が上がった」を区別でき、更新が本当に着地したかどうかが分かる。

インターフェイス全体が国際化されている。ユーザーに見えるすべての文字列 —— バックエンドのエラーメッセージも、フロントエンドの UI のテキストも —— は、BCP 47 のロケールコード（`en-US`、`de-DE` など）を鍵とするメッセージカタログを通る。**30 の言語**がバックエンドとフロントエンドの両方で**完全に翻訳されて出荷されている**: アラビア語、ベンガル語、中国語（簡体字と繁体字）、クロアチア語、チェコ語、デンマーク語、オランダ語、英語、フィンランド語、フランス語、ドイツ語、ヒンディー語、ハンガリー語、イタリア語、日本語、韓国語、ポーランド語、ポルトガル語、ルーマニア語、ロシア語、サンスクリット語、スロバキア語、スロベニア語、スペイン語、スウェーデン語、タイ語、トルコ語、ウクライナ語、ベトナム語。

その上に **18 の国別変種**が載る —— `en-GB`、`en-AU`、`en-CA`、`en-IN`、`en-NZ`、`en-ZA`、`de-AT`、`de-CH`、`fr-BE`、`fr-CA`、`fr-CH`、`es-AR`、`es-MX`、`pt-PT`、`nl-BE`、`ar-AE`、`ar-EG`、`bn-IN` —— 合わせて**選択可能なロケールは 48** となる。変種は二つ目の翻訳ではない。その言語のカタログを継承し、その国が実際に別の言い方をする文字列だけを並べるので、新しいメッセージは基底の言語がそれを持った瞬間にすべての国へ届き、フランス語の文字列の修正は四つのファイルではなく一度で済む。それらの上書き一覧のいくつかは、正直に空である。カナダ英語はアメリカ式の *-ize* の綴りを保つし、アルゼンチンのスペイン語は *voseo* で有名だが、voseo が置き換えるのは親しい *tú* であり、このカタログは終始読者を *usted* で呼ぶので、ブエノスアイレスでもマドリードでも同じに読める。空の一覧も、忘れられたのではなく検討済みであることを意味する。System Settings の言語画面は、よく使われる 21 の言語をその言語自身の文字で示し、国別の 89 のコードを展開できる一覧として添える。カタログの無いものは表示されるが選べない。

UI はあなたの言語をブラウザ（`navigator.languages`）から選ぶ。まず完全一致が勝つので、`de-CH` はドイツのものに畳まれるのではなくスイスのドイツ語になる。中国語は文字体系で区別される。我々が何も用意していない国は、実際に読まれている方へ行く —— `es-CO` は半島のスペイン語ではなくメキシコのスペイン語へ、`en-IE` はアメリカ英語ではなくイギリス英語へ —— そして裸の `en` や `pt` は、たまたま最初に読み込まれた変種ではなく、名前の付いた既定値に解決される。明示的な選択はブラウザごとに記憶されるので、機械の全体設定としての言語が各人の見るものを上書きすることはもう無い —— それは Town OS がカタログを持たない言語のためのフォールバックにすぎない。

Windows のアプリケーションは、Valve の Proton 互換レイヤーを通じてネイティブな Linux コンテナと並んで動かせる。`proton` セクションを持つパッケージ定義が、Windows アプリのイメージ、展開先のディレクトリ、実行ファイルのパスを指定する。システムは OCI イメージからアプリを取得し、永続ボリュームへ展開し、Proton ランナーのコンテナ内で実行する。ランナーのイメージはシステム全体の `proton_image` 設定で構成する。**Proton のサポートはオプトインである**: `make PROTON_ENABLED=1 …`（または `go build -tags proton`）で再ビルドして初めて組み込まれる。このタグが無ければ、パッケージ YAML の `proton:` ブロックはインストール時に拒否され、`proton_image` の設定は投入されず、Settings の UI は Proton のカードを省き、リリースのパイプラインはランナーのイメージをビルドも push もしない。

組み込みの監視スタックが、そのままでシステムの可観測性を提供する。Prometheus がメトリクスを収集し、Node Exporter がホストレベルの統計を報告する。どちらもシステムサービスとして管理され、手作業の設定は要らない。ダッシュボードは既定では uPlot（約 35 KB）で UI に直接描かれる —— ディスク I/O、ネットワーク、CPU、メモリ —— これにより約 771 MB の Grafana イメージを機械から完全に締め出せる。`monitoring_backend` の設定を `grafana` に切り替えれば、代わりに Grafana のスタック一式が取得・起動され、データソースと二つのダッシュボードがあらかじめ用意される。

QEMU の仮想マシンのサポートが、コンテナと並ぶ一級のランタイムとして動く。パッケージは `image:` の代わりにトップレベルの `vm:` セクション —— ディスクイメージ、メモリ、CPU 数 —— を持つだけでそれを選べる。Control Plane Service が URL からイメージをダウンロードし、`qemu-img` で raw 形式へ変換し、`vm-images` の btrfs サブボリュームにキャッシュする。インストール時には、systemd のサービスユニットが KVM による高速化、virtio のネットワーク、ユーザーモードのポートフォワードを伴って `qemu-system-x86_64` を起動する。VM のイメージは API と UI から一覧、アップロード、削除ができる。

静的な page のホスティングにより、HTML の内容を UI から直接公開できる。三つのソース種別に対応する: tar アーカイブのアップロード（既定）、コンテナイメージからのファイルの取り出し、git リポジトリの clone である。作成ダイアログのドロップダウンでソース種別を選ぶ。各 page は共有 ingress を通じて自分のドメインで HTTPS で提供され、証明書はローカルの CA が発行する。page はパッケージと同じくネットワークに属するので、サイトを LAN 上の全員に公開することも、一つの WireGuard ネットワークのピアだけに公開することもできる。アーカイブの page はいつでも新しいアーカイブをアップロードして更新でき、git とコンテナイメージの page は必要に応じて再ビルドして最新の内容を取り込める。

[スクリーンショット](./screenshots/)をいくつか見てほしい。これらはすべて、今日の開発用のタスクで動いている。

パッケージングシステム、ストレージ、pages、API のドキュメントを含む詳しい使い方は **<https://town-os.github.io>** を参照のこと。

## 起動可能なイメージ（PC と Raspberry Pi）

このリポジトリには Town OS のソフトウェアが入っている。**起動可能なディスクイメージ**は別の [install リポジトリ](https://gitea.com/town-os/install)からビルドされ、そこから VM で起動することもできる:

```bash
git clone https://gitea.com/town-os/install.git
cd install
make deps        # 一度だけ、手作業で —— どのビルドターゲットもパッケージをインストールしない
make run         # イメージをビルドして VM で起動する
```

イメージのビルドは既定ではネイティブである —— `TARGET` を指定しなければ、イメージのアーキテクチャはビルドホストに一致する。別のものを指定するには `TARGET` を使う:

| コマンド                    | 結果                                                                        |
| -------------------------- | ----------------------------------------------------------------------------- |
| `make image TARGET=x86_64` | PC 向けイメージ（UEFI/GRUB）。x86_64 のホスト専用 —— x86 のエミュレーション経路は存在しない。 |
| `make image TARGET=aarch64`| 汎用の aarch64 イメージ（UEFI/GRUB）。Apple Silicon の VM など。                  |
| `make image TARGET=rpi`    | **ネイティブに起動する Raspberry Pi 向けイメージ。** 一つのイメージで Pi 4/400/CM4 と Pi 5/CM5 を賄う。|

**Raspberry Pi。** `TARGET=rpi` は aarch64 専用かつ btrfs 専用であり、GRUB ではなく Pi 自身の GPU ブートローダーと `config.txt` で起動する。aarch64 のホストではネイティブにビルドされ、x86_64 のホストではフルシステムの `qemu-system-aarch64` VM の中で交差生成される —— `binfmt`/qemu-user でもクロスコンパイラでもなく、まるごと一台のエミュレートされた機械なので、ビルドは依然としてネイティブな aarch64 のコードとして走る。動くが、遅い。

出来上がった `-rpi` のイメージを SD カード、USB メモリ、NVMe へ書き込む:

```bash
make flash RPI=1 USB_DEV=/dev/sdX   # または town-os-<date>-aarch64-rpi.img を dd する
```

**Pi 5 の NVMe からの起動**では、EEPROM の起動順序に NVMe を含めるよう設定すること（`rpi-eeprom-config --edit` → `BOOT_ORDER=0xf416`。HAT+ 以外のアダプタでは `PCIE_PROBE=1` も加える）。`dtparam=pciex1` は生成される `config.txt` に既に入っている。USB の電流上限は両方の基板について `config.txt` で既に解除されている（Pi 5 では `usb_max_current_enable=1`、Pi 4 では `max_usb_current=1`）。これが効いてくるのは、バスから給電される USB の SSD や NVMe のアダプタこそが USB 起動のイメージの走る先であり、ファームウェアの既定値では電圧が落ち込んでしまうからである。

書き込み、シリアルコンソール、リリース、変数の全一覧については [install リポジトリの README](https://gitea.com/town-os/install) を参照のこと。

## 前提条件

まっさらな機械での近道は `make deps` である:

```bash
make deps
```

これは Arch 系および Debian/Ubuntu 系のディストリで、ホスト側の依存関係（Go 1.25、podman、runc、btrfs-progs、libsystemd のヘッダ、golangci-lint、bun、qemu、ビルドツール）をすべてインストールする。さらに `ui/` で `bun install` も実行するので、UI のツールチェイン（eslint、vite、vitest）が `make lint` と `make test` のために整う。再実行しても安全である。

Town OS がホストに必要とするものの全一覧:

- Go 1.25+
- [Bun](https://bun.sh)（JS ランタイム。`ui/` の devDeps には eslint、vite、vitest が含まれ、`make deps` が自動でインストールする）
- Podman（rootful、`sudo` 付き）と `runc` ランタイム
- VM パッケージのサポートのための QEMU（`qemu-system-x86_64`、`qemu-img`）
- btrfs-progs（`mkfs.btrfs`）
- libsystemd（systemd との統合のための開発ヘッダ）
- golangci-lint
- Python 3（テストのターゲットでのポート割り当てに使う）

すべて手作業でインストールしたい場合、以下のコマンドは `make/deps.sh` がしていることをなぞったものである。

### Ubuntu / Debian

```bash
sudo apt-get update
sudo apt-get install -y build-essential pkg-config ca-certificates libsystemd-dev \
    btrfs-progs podman runc python3 curl git unzip qemu-system-x86 qemu-utils
```

Go 1.25+ を <https://go.dev/dl/> からインストールし、続いて:

```bash
curl -fsSL https://bun.sh/install | bash
curl -sSfL https://raw.githubusercontent.com/golangci/golangci-lint/HEAD/install.sh | sh -s -- -b $(go env GOPATH)/bin
(cd ui && bun install)
```

### Arch Linux / Manjaro

```bash
sudo pacman -Sy --needed base-devel pkgconf systemd btrfs-progs podman runc \
    python curl git unzip qemu-base qemu-img golangci-lint go
```

続いて:

```bash
curl -fsSL https://bun.sh/install | bash
(cd ui && bun install)
```

必要に応じて、**dev 環境**用にリポジトリの資格情報を書いた `.env` ファイルを作る:

```
TOWN_OS_REPO_USERNAME=<username>
TOWN_OS_REPO_PASSWORD=<password>
```

これらは `make dev` がバックエンドに既定のリポジトリの資格情報を設定するために使う。パスワードには Gitea や GitHub の HTTP API キーを使ってよい。省略した場合は既定の資格情報が設定されず、明示的な資格情報なしに追加できるのは公開リポジトリだけになる。

統合テスト（`make test-full`）は `.env` の資格情報を**使わない**。ハードコードされたテスト用の資格情報（`town-os` / `town-os-test`）でローカルの Gitea インスタンスを動かし、リポジトリの操作で GitHub に接続することは一切ない。

前提条件をインストールしたら、`make pull-images` を一度実行して、すべてのコンテナイメージを Docker Hub から取得し、このチェックアウトのイメージキャッシュ `.cache/images/` に保存すること。Docker Hub の資格情報（`.env` の `DOCKER_USERNAME` / `DOCKER_PASSWORD`）が必要になるのは、レート制限に当たった場合だけである。他のビルドとテストのターゲットはすべてそのキャッシュからイメージを読み込み、Docker Hub に接続することはない。ターゲットが必要とするキャッシュ済みのイメージが欠けている場合は、`make pull-images` が自動的に実行される。

## 開発

> **まっさらな機械ではここから:**
>
> - **`make deps`** —— Arch または Ubuntu/Debian で、ホスト側の依存関係（Go、podman、runc、btrfs-progs、libsystemd のヘッダ、golangci-lint、bun、qemu、ビルドツール）をすべてインストールする。再実行しても安全である。
> - **`make help`** —— ユーザー向けの make ターゲットをグループ分けして一覧表示する。これは既定のターゲットでもあるので、素の `make` でも動く。

**dev サーバーの実行中に統合テストを走らせると、まだ未解決の問題がいくつか残っている可能性がある。調査中である。**

ちょっと試してみたいだけなら `stable` ブランチ（既定）を使うこと。最新の変更（良い状態とは限らない）が欲しいなら `main` を使うこと。どちらのブランチも、安定と判断されたりリポジトリへ統合されたりするのに従って進んでいく。

`make dev` を実行すると、テストイメージをビルドし、dev 用の btrfs ボリュームを作り、ポート 5309 でバックエンドのコンテナを起動し、ホットリロード付きの Vite の開発サーバーを立ち上げる。起動したら `http://<hostname>:5173` で UI にアクセスする。

ホスト上でポート 5309（バックエンド API）と 5173（Vite の開発サーバー）にアクセスできる必要がある。

| ターゲット               | 説明                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------- |
| `make dev`           | dev 環境一式を起動する（バックエンド + Vite の開発サーバー）。                                 |
| `make dev-stop`      | この作業ツリーの dev バックエンドのコンテナを停止して削除する。                            |
| `make dev-stop-all`  | この作業ツリーのものだけでなく、ホスト上のすべての `town-os-dev-*` コンテナを停止する。             |
| `make dev-logs`      | 動作中の dev コンテナ内の journalctl を追尾する。                                           |
| `make btrfs-dev`     | dev 環境用に 50GB の btrfs ループバックボリュームを新しく作る。                          |
| `make dev-btrfs`     | まだマウントされていない場合にのみ dev の btrfs ボリュームを作る（`dev` が自動で使う）。|
| `make clean-btrfs-dev` | dev の btrfs ボリュームをアンマウントし、loop デバイスを切り離し、削除する。                            |
| `make clean-dev`     | dev のコンテナを停止し、dev の btrfs ボリュームを片付ける。`dev-data/` を削除する。             |

## Makefile のターゲット

すべてのターゲットは作業ディレクトリのパスから導かれる一意な `INSTANCE_ID` を使うので、複数のチェックアウトが衝突せずに同時に動ける。一時的な状態（ポートファイル、btrfs のボリューム、dev のデータ）は `/tmp/town-os-$(INSTANCE_ID)/` にある。

### テスト

| ターゲット                          | 説明                                                                                                                                          |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `make test`                     | lint、Go のユニットテスト、JS のユニットテストを実行する。                                                                                          |
| `make test-race`                | lint と Go のユニットテストを race detector の下で実行する。`test` より遅く Go 専用（bun に相当するものは無い）。ゲートとしてではなく、切り分けのための報告として使う。 |
| `make test-integration`         | テストイメージをビルドし、systemd と btrfs を備えた特権付きの podman コンテナ内で Go の統合テストを実行する。終了時に btrfs のループバックを片付ける。     |
| `make test-integration-build`   | テストイメージをビルドし、すべてのイメージを読み込んだ状態で統合テストのコンテナを起動するが、テストは実行しない。`test-integration-rerun` の準備に便利である。 |

どの統合テストを走らせるかを絞るには `TEST_RUN=<regex>` を使う（例: `make test-integration TEST_RUN=TestInstall`）。既定の 60 分のタイムアウトを上書きするには `TEST_TIMEOUT=<duration>` を使う。

**テストの実行が、別の実行や `make dev` と衝突することは決してない。** テストコンテナはホストネットワークで動く（意図的である —— ブリッジネットワークの DNS はキャプティブなネットワークで壊れる）ので、それが起動するシステムサービスはすべてホストのネットワーク名前空間にバインドされる。`make dev` が起動するものも同様である。したがってハーネスは実行ごとに、rolodex、node-exporter、Prometheus、監視の UI、ingress のための専用の一時ポートと、専用の WireGuard のソルトを渡す。これにより、インターフェイス名、listen するポート、オーバーレイのサブネットがチェックアウトごと・役割ごとに異なるものになる。`make dev` はこれらの上書きをあえて一切受け取らない。DNS が `:53` に、ingress が `:443` にある実機を模すことが目的だからである。

### ローカルの Registry

統合テストは Docker Hub のレート制限を避けるためローカルの `registry:2` コンテナを使う。`make test-integration` や `make test-ui-integration` を実行すると、ビルドは自動的に:

1. テスト用のパッケージリポジトリが参照する `docker.io` のイメージをすべて探し出す（`discover-images` ツール）
2. ランダムなポートでローカルの registry を起動する
3. 各イメージをイメージキャッシュから読み込み、ローカルの registry へ push する
4. `docker.io` からの pull をローカルのミラーへ向け直す `registries.conf` を生成する
5. その設定をテストコンテナへマウントする

これは透過的である —— コードの変更は要らない。すべてのイメージはチェックアウトのイメージキャッシュ（`.cache/images/`）から読み込まれ、テストのパイプラインの間に docker.io からの pull は発生しない。

| ターゲット                   | 説明                                               |
| ------------------------ | --------------------------------------------------------- |
| `make registry`          | ローカルの registry のコンテナを起動する。                       |
| `make registry-populate` | 見つかった docker.io のイメージをローカルの registry へミラーする。 |
| `make registry-stop`     | ローカルの registry のコンテナを停止して削除する。             |

作業ディレクトリごとに（`INSTANCE_ID` によって）専用の registry インスタンスが割り当てられるため、同時に走るテストは衝突しない。

### ローカルの Gitea サーバー

統合テストは、テスト用のパッケージリポジトリを GitHub から直接 clone しないようにするため、ローカルの Gitea インスタンスも使う。`make test-integration` や `make test-ui-integration` を実行すると、ビルドは自動的に:

1. ランダムなポートでローカルの Gitea サーバーを起動する
2. 管理者ユーザーを作る
3. テスト用のパッケージリポジトリを `.cache/git-repos/` に bare clone としてキャッシュする（以後の実行では fetch して更新する）
4. キャッシュしたリポジトリを go-git で Gitea へ push する（`populate-repos` ツール）
5. `TOWN_OS_TEST_REPO_CORE_URL` と `TOWN_OS_TEST_REPO_EXTRAS_URL` の環境変数をテストコンテナへ渡し、git の clone がすべてローカルの Gitea インスタンスに向かうようにする

`.cache/git-repos/` の bare clone のキャッシュは Gitea の再起動をまたいで残るので、GitHub に当たるのは最初の実行だけである。以後の実行では更新を fetch し、新しい Gitea インスタンスへ push する。`make clean` がこのキャッシュを削除する。

これは透過的である —— コードの変更は要らない。環境変数が設定されていない場合、テストは GitHub の URL にフォールバックする。

| ターゲット                | 説明                                                |
| --------------------- | ---------------------------------------------------------- |
| `make gitea`          | ローカルの Gitea コンテナを起動し、管理者ユーザーを作る。 |
| `make gitea-populate` | テスト用のリポジトリを GitHub からローカルの Gitea へ移す。       |
| `make gitea-stop`     | ローカルの Gitea コンテナを停止して削除する。                 |

作業ディレクトリごとに（`INSTANCE_ID` によって）専用の Gitea インスタンスが割り当てられるため、同時に走るテストは衝突しない。

### リリースと push

リリースのイメージはすべて `quay.io/town/` へ push される。push するタグはすべてアーキテクチャごとに分割されている。各ホストは自分のネイティブなアーキテクチャを `rc.<date>-<arch>` / `rc.latest-<arch>`（リリース候補）または `release.<date>-<arch>` / `latest-<arch>`（リリース）として push する。ここで `<arch>` は生の `uname -m` の形式 —— `x86_64` または `aarch64` であり、OCI のプラットフォーム名 `amd64`/`arm64` では*ない*。素の名前（`rc.latest`、`latest`、および日付タグ）は、すべてのアーキテクチャが push を終えたのちに `make manifest-rc` / `make manifest-release` が組み立てるマルチアーキテクチャのマニフェストリストとしてのみ存在する。素の名前を単一アーキテクチャのタグとして push してはならない。もう一方のアーキテクチャで `exec format error` により失敗するからである。

実行時、システムコントローラは兄弟のイメージのタグ（UI、Rolodex、ネットワークコントローラ、ingress）をすべて単一の値から導く。`TOWN_OS_TAG` の環境変数が設定されていればそれ、そうでなければ `rc.latest-<arch>` である。コンパイル時のバージョンの固定は無い —— install のビルドシステムがリリースを固定するためにシステムコントローラの systemd ユニットに `TOWN_OS_TAG` を設定し、上書きが無ければ機械は常に `rc.latest-<arch>` を追う。

| --------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `make release-image`        | リリース用のシステムコントローラのイメージをビルドする（`quay.io/town/town`）。                                                   |
| `make release-ui-image`     | リリース用の UI イメージをビルドする（`quay.io/town/ui`）。                                                                    |
| `make release-proton-image` | リリース用の Proton ランナーのイメージをビルドする（`quay.io/town/proton`）。**`PROTON_ENABLED=1` が必要**。そうでなければこのターゲットは存在しない。 |
| `make release-nc-image`     | リリース用のネットワークコントローラのイメージをビルドする（`quay.io/town/networkcontroller`）。                                     |
| `make release-ingress-image`| リリース用の ingress のイメージをビルドする（`quay.io/town/ingress`）。                                                          |
| `make release-build`        | イメージを pull し、`test-full` を実行し、そのうえでリリースのイメージをビルドする。`PROTON_ENABLED=1` のときは Proton ランナーも含む。    |
| `make push`                 | `push-rc` の別名。                                                                                               |
| `make push-rc`              | すべてのイメージ（システムコントローラ、UI、ネットワークコントローラ。`PROTON_ENABLED=1` のときは Proton も）をアーキテクチャ別のリリース候補（`rc.<date>-<arch>` + `rc.latest-<arch>`）として push する。 |
| `make manifest-rc`          | アーキテクチャ別のタグから素の `rc.<date>` / `rc.latest` のマルチアーキテクチャのマニフェストリストを組み立てて push する。すべてのアーキテクチャが push を終えたあと一度だけ実行する。 |

| `make manifest-release`     | アーキテクチャ別のタグから素の `release.<date>` / `latest` のマルチアーキテクチャのマニフェストリストを組み立てて push する。すべてのアーキテクチャが push を終えたあと一度だけ実行する。 |
| `make push-ui-rc`           | UI のイメージだけをアーキテクチャ別のリリース候補（`rc.<date>-<arch>` + `rc.latest-<arch>`）として push する。                  |

### Btrfs の管理

| ターゲット                 | 説明                                                                 |
| ---------------------- | --------------------------------------------------------------------------- |
| `make btrfs`           | 統合テスト用に 50GB の btrfs ループバックボリュームを作る。                  |
| `make clean-btrfs`     | 統合テストの btrfs ボリュームをアンマウントし、loop デバイスを切り離し、削除する。 |
| `make btrfs-dev`       | dev 環境用に 50GB の btrfs ループバックボリュームを作る。                |
| `make clean-btrfs-dev` | dev の btrfs ボリュームをアンマウントし、loop デバイスを切り離し、削除する。              |
| `make dev-btrfs`       | まだマウントされていない場合にのみ dev の btrfs ボリュームを作る。              |

dev と統合テストの環境は btrfs のボリューム、コンテナイメージ、ビルドキャッシュを別々に使うので、衝突せずに同時に動かせる。

### クリーンアップ

`make test-full` はテストの完了後、統合テストのコンテナ、registry、Gitea、btrfs のループバックボリュームをすべて自動で片付ける。シェルの EXIT トラップにより、シグナルで中断された場合でもクリーンアップが確実に走る。各統合テストのターゲット（`test-integration`、`test-ui-integration`）も自前の EXIT トラップを使い、レシピがどう終わったか（成功、失敗、シグナルによる中断）に関わらず btrfs のループバックの片付けを保証する。`clean-btrfs` ターゲットには、カレントディレクトリの btrfs イメージを裏に持つ孤児の loop デバイスを走査する安全網があり、追跡用ファイルが失われている場合にも対処する。

| ターゲット                   | 説明                                                                             |
| ------------------------ | --------------------------------------------------------------------------------------- |
| `make clean`             | `.cache/` のビルドキャッシュのディレクトリを削除する。                                             |
| `make clean-dev`         | すべての dev コンテナを停止し、dev の btrfs を片付け、dev-data/dev-repos を削除する。                |
| `make clean-cache`       | 一時的な状態のディレクトリから dev のデータ、dev のリポジトリ、dev の Rolodex のデータを削除する。    |
| `make clean-integration` | 統合テストのコンテナ（test、UI バックエンド、UI ランナー）を削除し、btrfs を片付ける。       |
| `make clean-btrfs`       | 統合テストの btrfs ボリュームと孤児の loop デバイスをアンマウントして削除する。         |
| `make clean-image-cache` | このチェックアウトのイメージキャッシュ（`.cache/images/`）を削除する。                           |
| `make clean-containers`  | 作業ディレクトリ／インスタンスを問わず、すべての town-os と preflight のコンテナを削除する。      |
| `make clean-all`         | すべてを片付ける: 全コンテナ、ビルドキャッシュ、dev、統合テスト、btrfs。             |
